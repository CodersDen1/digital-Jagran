# Production considerations and acceptance register

Updated: 20 October 2026 (Asia/Kolkata).

This register maps the requested idempotency requirement and every numbered topic, 1–110. It describes decisions, responsibility and acceptance evidence; it is **not a claim that the system has been deployed, load-tested, audited or certified**. Implementation is changing alongside this document. A row is complete only when its stated evidence has been recorded against the deployed version.

## Selected production baseline

The selected platform is Kubernetes. The proposed initial topology is one region, multiple application replicas, a managed MongoDB **replica set**, an HTTPS ingress, and an optional CDN serving public assets. Public site rendering, the newsroom UI and the JSON API share an application release. MongoDB holds authoritative articles, subscriber consent, shared sessions, shared rate-limit state and durable idempotency records. Container-local JSON storage is for development only. Do not put the file store on a shared volume to make it appear safe for multiple writers.

Start with two application replicas spread across separate nodes; use separate availability zones where the chosen cluster supports them. This is a starting configuration to validate, not a capacity commitment. Configure a disruption budget and a rolling deployment that retains available capacity. The actual cloud, ingress controller, domain, MongoDB tier, zone layout, image registry, telemetry service and backup retention remain deployment decisions. Kubernetes alone does not supply a production ingress, certificates, database, WAF, monitoring backend or an on-call team.

Shared state is a release prerequisite: an authenticated request and its retry must behave correctly when routed to different pods. Sticky sessions must not be used to hide process-local state. Cross-pod cache invalidation and database connection budgets must also work during rolling deployments and autoscaling.

### Interpretation of status

- **Required:** applicable to this release; implement or configure it and collect acceptance evidence before launch.
- **Conditional:** activate when the named integration or workload exists; the stated boundary still applies now.
- **Deferred:** intentionally omitted because the baseline has no corresponding requirement. The row states the trigger for reconsideration.
- **Operational:** primarily an infrastructure or human responsibility; application code cannot prove completion.

Owners in the tables are responsibility categories: **App**, **Platform**, **DB**, and **Operations**. Assign named people before launch. A configuration file or passing unit test is useful evidence, but does not prove the corresponding cloud control is active.

## Implementation and deployment boundaries

### Proxy identity, transport and deadlines

Express must trust only the actual ingress path. The trusted edge must replace incoming forwarding headers; allowing arbitrary `X-Forwarded-For`, host or protocol values undermines IP limits and origin decisions. Test both the intended ingress and attempted direct access. This is based on the official [Express reverse-proxy guidance](https://expressjs.com/en/guide/behind-proxies/).

Separate upload/header receipt limits, application execution deadlines, database operation limits, upstream proxy timeouts and the termination budget. Node's request timeout concerns receiving a request; it is not a general handler deadline. Stop accepting work during shutdown, finish bounded in-flight requests, then close the database client. Force connection closure only after the drain deadline and record any interrupted requests. Confirm the deployed Node version's behavior against the [Node HTTP documentation](https://nodejs.org/download/release/latest-v24.x/docs/api/http.html).

Candidate ordering to validate: database execution ≤ 5 seconds, application deadline ≤ 10 seconds, ingress response deadline about 15 seconds, and pod termination grace at least 30 seconds. These values are **proposed settings**, not measured behavior. An HTTP timeout must not be presented as proof that a database write was cancelled. Resolve unknown write outcomes through the idempotency record before allowing another attempt.

### MongoDB pooling, writes and indexes

Reuse one driver connection pool per application process. Budget connections for the maximum replica count **plus rollout surge**, and include topology monitoring sockets. Explicitly configure pool acquisition wait and server selection deadlines; a finite pool alone does not bound wait duration. Bound database operation time independently. The official [Node driver pooling guide](https://www.mongodb.com/docs/drivers/node/current/connect/connection-options/connection-pools/) and [connection options reference](https://www.mongodb.com/docs/drivers/node/current/connect/connection-options/) explain these separate controls.

Keep article content and its revision in one document where practical. Use a conditional atomic update for optimistic locking. For create requests, commit the content mutation and durable idempotency result together when they occupy separate documents. A replica set and a tested transaction path are therefore requirements for this baseline, rather than assuming a unique key alone gives exactly-once effects. Keep transactions short and exclude network calls. See MongoDB's [transactions guide](https://www.mongodb.com/docs/manual/core/transactions/) and [production considerations](https://www.mongodb.com/docs/v8.0/core/transactions-production-consideration/).

Create and inspect unique indexes before exposing writes. Clean existing duplicates and invalid legacy rows through a backed-up migration; do not silently discard them. Use query plans and realistic data to verify article lookup, publication filtering and pagination. Indexes are workload decisions and carry write/storage costs. See MongoDB's [unique indexes](https://www.mongodb.com/docs/manual/core/index-unique/) and [index creation](https://www.mongodb.com/docs/manual/core/indexes/create-index/) documentation.

### Probe and secret boundaries

Use distinct startup, liveness and readiness meanings. Readiness includes the ability to serve the promised workload and fails during drain. Liveness detects a stuck process; a shared database outage should not trigger a restart storm across all pods. Validate thresholds against real startup behavior. See the official [probe guidance](https://kubernetes.io/docs/tasks/configure-pod-container/configure-liveness-readiness-startup-probes/).

Inject credentials through an existing secret reference or external secret manager. Do not commit secret values in Helm values or manifests. Enable cluster secret encryption, restrict read access and rehearse rotation; a base64 value is not encryption. See [Kubernetes Secrets](https://kubernetes.io/docs/concepts/configuration/secret/). Configure rollout and termination together and test them under traffic using the [Deployment](https://kubernetes.io/docs/concepts/workloads/controllers/deployment/) and [Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) references.

## Proposed SLOs and measurement contracts

These are **candidate targets requiring owner approval and staging evidence**. They are not established performance results. Measure public service at the edge and editorial operations at the authenticated API; monitor content correctness separately from transport success.

| Journey | Candidate target | Measurement and caveat |
|---|---|---|
| Public article/home delivery | 99.9% good eligible requests over rolling 30 days | A good request has the expected status and usable content; include edge/origin failures. Separate legitimate 404s and explicit abuse rejections. Missing published content or cached draft leakage is a correctness incident even with HTTP 200. |
| Public uncached HTML latency | p95 ≤ 800 ms; p99 ≤ 2 s at selected regional edge | Measure TTFB with representative content, concurrency and cold/warm states. Establish a separate audience/browser page-experience baseline. |
| Editorial save/publish | 99.9% successful eligible operations; p95 ≤ 1 s | Count an operation by durable key/revision, not each retry. Valid conflicts and input errors are classified separately; unknown outcomes must be resolved. No acknowledged mutation loss is acceptable. |
| Publication/correction visibility | Visible on every application replica within 5 seconds; edge within 30 seconds if enabled | Test home, section, article, both locales and sitemaps. Decide whether the candidate edge delay is acceptable for corrections and emergency takedowns; disable HTML edge cache if not. |
| Restore readiness | Candidate RPO ≤ 15 minutes; RTO ≤ 2 hours | Requires managed PITR/backup plan and a completed restore drill. If the selected tier cannot meet these, change the objective explicitly rather than implying it is satisfied. |

For a 99.9% availability target, the error budget is 0.1% of eligible requests. A 30-day time-based equivalent is 43.2 minutes, but the requested-event SLI must use request counts; the equivalent is illustrative only. Use a fast and a slow burn window to avoid paging on isolated noise. Start with manual review of releases when the budget is exhausted; set exact burn thresholds with the operating team.

## Backup and restore runbook

1. **Inventory and protect:** identify the managed Mongo project/cluster, backup/PITR capability, retention, restore permissions, encryption keys, object/media storage, secret references and infrastructure state. Assign an owner. Keep restore credentials separately accessible during a cluster outage.
2. **Create recovery evidence:** before a risky migration, create/confirm a provider-consistent backup or recovery point and record its timestamp, deployment version and retention. Use provider-supported backup procedures. If using Mongo tools instead, select a consistency strategy appropriate to concurrent writes and replica-set topology; a casual dump of a busy database is not proof of a consistent backup. See the official [backup/restore tools guidance](https://www.mongodb.com/docs/manual/tutorial/backup-and-restore-tools/).
3. **Restore in isolation:** restore to a new non-public cluster/database using a separate namespace and least-privilege credentials. Disable newsletter delivery, outbound integrations and background side effects. Do not point a validation environment at production write credentials.
4. **Validate:** compare expected collection counts and sampled hashes, inspect index definitions, confirm bilingual article bodies/images/sources, subscriber consent, and schema compatibility. Check idempotency records so retained operations cannot be duplicated after recovery. Invalidate/revoke restored sessions according to the incident policy. Do not blindly replay pending operational records.
5. **Measure:** record the newest recovered write (actual RPO), time to verified service (actual RTO), failures and missing dependencies. A failed test becomes a tracked release blocker when it contradicts the approved recovery objective.
6. **Cut over only under incident authority:** stop or fence old writers, establish a single active write target, update secret references/endpoints, roll the application, verify private and public journeys, and purge stale content caches. Keep the old environment read-only for evidence where appropriate.
7. **Close out:** rotate credentials touched during recovery, confirm backups cover the new target, remove temporary access and securely retire the validation copy under retention policy. Repeat after significant database/schema changes and on an agreed calendar.

## Release and rollback runbook

1. Record current/previous application image digests, Helm revision, configuration/secret references, compatible schema range and backup point. Deploy the same immutable artifact tested in staging.
2. Apply additive database/index preparation independently where needed. Avoid destructive migration during a rolling release. Confirm old and new pods understand the overlap period's documents and shared session/idempotency formats.
3. Roll out with readiness, capacity and drain limits. Watch external public journeys, editorial writes, error/latency burn, pool wait and content freshness. Abort if correctness, acknowledged-write durability or privacy fails, even if CPU looks healthy.
4. For an application regression, select the known-good image/chart revision and compatible configuration. Perform a Helm rollback or deploy that pinned artifact through the normal pipeline. This changes application resources; it does not reverse Mongo data or restore a backup automatically.
5. If the database has changed incompatibly, first stop/fence unsafe writes and use a reviewed forward fix or recovery plan. Never run an unreviewed destructive “down” migration just to make the old binary start. Preserve writes made since the recovery point or explicitly account for their loss.
6. Verify both locales, authentication, saved editorial drafts, new create/retry behavior, publishing, archive visibility, metrics and certificates. Confirm rollout convergence and no old incompatible pods remain.
7. Record outcome, affected content, unknown operations resolved, cache actions and evidence; open an incident/postmortem when user impact warrants it.

## Incident response and deferred capabilities

For elevated errors, first determine whether the failure is edge, application, database or a single release. Check public synthetic journeys and recent deployment changes; use route-template metrics and request IDs without exposing article drafts or subscriber data. Mitigate by rollback, reducing expensive load or restoring a failed dependency. Preserve idempotency/revision evidence when a write's outcome is unknown. Do not tell editors to repeatedly press Publish or to clear recovery storage to resolve a server failure.

For unintended publication or draft leakage, stop the affected public path or reverse the publication through an authorized write, purge every active cache, and verify externally from both locales. Record exactly what was exposed and for how long; do not assume `robots.txt` withdraws already served content.

WebSockets, SSE, long polling, gRPC, sharding, cross-service sagas, a general message broker and active/active multi-region deployment are intentionally deferred. They add failure modes and operational ownership without meeting a current first-party publishing requirement. Add one only when a concrete feature, measured bottleneck or approved recovery objective requires it, together with its contract, acceptance tests and runbook.
